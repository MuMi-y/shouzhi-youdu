## 公式与适用条件

用 `C0` 表示当前已到账余额，`I_s(t)`、`O(t)` 表示截至日期t的累计收入和累计已登记支出，s表示不同收入条件：

`B_s(t) = C0 + I_s(t) − O(t)`

对于在日期τ增加的一次性支出、其余安排保持不变，且原计划在所有更早日期可行时：

`H_s(τ) = max(0, min_{t∈[τ,T]} [B_s(t) − R(t)])`

其中R(t)是该情景要求的保留金额。H是有条件余量，不是风险概率、银行授信额度或对未知未来的保证。若本来就不足，H显示0仍必须同时展示已有缺口；零新增消费不代表原计划已变得可行。新增收入、分期支出或会改变其他安排的动作，需要重新跑完整路径，不能直接套单笔公式。

反推当前至少需要的资金：

`C_required_s = max(0, max_t [R(t) + O(t) − I_s(t)])`

本例R恒为3,000：计入预计收入时需16,000，当前余量2,000；不计未来收入时需26,000，已有8,000保留不足、可新增余量0。历史月均收入10,000并不自动成为I_s(t)；预计收入须有登记依据和日期，并保留未到账情景。

## 目前怎样触发AI

确定性核对先执行，再比较目标版本与状态、方案可行性、收入条件、用户选择、截止窗口、当前计划通知状态、安排和保留线突破等签名。依据未变复用记录；无关键变化为QUIET；有变化但未启用模型为NO_MODEL；启用时进入PENDING并排队。Worker、模型、预算和依赖可用才可能完成实际分析。

新事实使旧排队或运行结果成为STALE；开始和结束均核对依据，校验通过才采用。排队不等于服务成功。失败/中断保留记录，可信恢复入口受限，不无限重试。

现有签名含“是否突破”的布尔量。已经突破后继续恶化，若其余签名字段不变，可能仍保持安静。因此本材料没有声称系统已具备“任何越界金额都会即时唤醒”的通用阈值策略，也没有编造节省调用百分比。

## 复现与范围

仓库根目录安装部署文档所需依赖后，执行：

```powershell
python submission/reproduce_algorithm_examples.py
```

脚本只调用纯预测函数，生成旁边的`algorithm-examples.json`，不读写运行数据库、不调用AI、不执行转账。JSON包含输入、逐日结果、场景摘要和`finance.py`的SHA256。断言针对示例数值，不能替代产品全量验收。

合并账户总余额充足不代表付款银行卡余额充足；实际执行仍需银行层单独校验。当前结果不包含未登记开销、真实银行接入、统计校准的收入置信度或日内到账顺序。独立统一阈值、卡片画像及长期用户减负效果均不能据此宣称已经完成。
